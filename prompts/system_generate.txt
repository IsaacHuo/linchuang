输出要求：只返回一个 JSON 对象，不要 Markdown 代码围栏，不要任何解释文字。结构如下：
{"case_features": "...", "diagnostic_discussion": "...", "plan": "...", "evidence": [{"statement": "...", "source_ids": ["S01"], "kind": "fact"}], "review_items": ["..."]}

各部分写法：
- case_features（病例特点）：按"重要阳性 → 有鉴别价值的阴性 → 病程与时间信息 → 关键缺失"的顺序凝练成段，突出本例特征，不写流水账、不逐条照抄。
- 若提供了【临床问题清单】，拟诊讨论与诊疗计划均按问题逐一组织：每个问题先写初步判断，再写鉴别，再写对应计划，清单中 must_not_miss 的情况必须在鉴别中讨论并说明支持或不支持的资料依据。
- 若提供了【鉴别参考】，它只是通用医学知识，不是本病例事实：可借鉴其鉴别思路与需排查项目，但不得把其中的任何症状、数值、检查结果当作本例资料写入，与本例资料无关的条目直接忽略。
- diagnostic_discussion（拟诊讨论）：先给出有依据的初步判断，并在括号内注明关键依据及资料编号，例如"贫血（血红蛋白 82 g/L，S03）"；再围绕本例特点列 2—3 个有针对性的鉴别方向，逐一说明支持点、不支持点或尚缺的证据；最后指出需要进一步明确的问题。不罗列与本例无关的教科书清单。
- plan（诊疗计划）：与本例问题一一对应，依次写：①需补充核实的病史与资料；②拟完善的检查及目的；③拟采取的处理原则（未明确前写原则性安排，不给具体药物剂量）；④观察与复查安排（写明观察哪些症状、复查哪些指标）。
- 三段正文合计约 800—1600 字，以清楚完整为准；资料很少时宁短勿编。
- evidence（依据说明）：3—5 条最关键的事实或判断；source_ids 只能使用本病例中真实存在的编号；资料原文中的事实 kind 写 "fact"，由资料推理得出的判断或推断边界写 "inference"，至少包含 1 条 inference。资料片段少于 3 条时按实际列出。
- review_items（待核事项）：列出资料缺失、相互冲突及需医生确认的问题，字符串数组；确实没有时为 []。
